Honest by design. DataSphere reports exactly what it validated, transferred and reconciled. It does not claim 100% accuracy: matching counts do not prove identical values, and a passing preview does not guarantee every record migrates.

This page is the in-application user guide. Follow the steps in order. Sidebar items with a phase badge (P3–P7) are documentation only and do not run yet.

  1. Open the application (development default: http://localhost:8080).
  2. Sign in with the administrator account configured for this environment.
  3. Go to Migration Projects and click New project. Give it a name (for example “Core banking pilot”).
  4. The workspace has five steps: Connections → Tables → Mapping → Validate & approve → Preview.

The development administrator exists only on your machine. Do not use it in production.

Source and target are chosen independently. They may be different products or the same product.

Supported types: Microsoft SQL Server (port 1433), Oracle (1521, service name), PostgreSQL (5432), MySQL (3306). Ports are editable.

  1. On the source card, pick the database type. Host, port, database or Oracle service name, user and password appear. Schema is optional except on MySQL, where the database name is the namespace.
  2. Click Test connection. Fix any error (host, port, login, driver, allow-list) before saving.
  3. Click Save connection. The password is kept in server memory only; it is never written to disk.
  4. Repeat for the target. Use a least-privilege account. The source should be read-only if your DBA can issue one.

After an application restart, open the project and enter both passwords again. Changing a connection to a different database clears the table selection and mapping.

  1. Open step Tables. Choose a source schema and a target schema (skip empty schemas such as PUBLIC if your objects live elsewhere).
  2. Click Load tables, or Suggest table pairs by name to match similar table names.
  3. Add pairs so each source table maps to one existing target table. Target tables must already exist; this build does not create them on the server.
  4. Click Save selection.

  1. Click Generate mapping suggestions. Suggestions use names, abbreviations, types and keys only — no AI and no sample data.
  2. Read every row: source column, type, suggested target, score, reason, status.
  3. A score around 60 with status Suggested usually means an abbreviation match (for example EMP_NM → EMPLOYEE_NAME). Confirm it; the band “needs review” is intentional.
  4. Use Accept, Reject, Clear, the target dropdown, or a conversion (trim, parse number, and so on). Incompatible types stay blocked until you pick a conversion.
  5. Leave a column unmapped if it must not be copied. Required target columns without a mapping will fail validation.

The engine never invents columns. One source column maps to at most one target column.

  1. Open Validate & approve and click Validate mapping.
  2. Fix errors (duplicates, required unmapped targets, incompatible types, mappings still waiting for review). Warnings (optional unmapped columns) do not block you.
  3. Tick I have reviewed every mapping…
  4. Click Approve Mapping & Continue and confirm. Approval is stored on the server with version, mapping hash, metadata fingerprint, user and time.

Changing the mapping, table list, database type or live table structure withdraws approval. The browser cannot bypass this.

  1. Run migration preview — re-checks approval, counts source rows, shows INSERT and generated CREATE TABLE text. Writes nothing.
  2. Start migration — confirm that INSERT into the target is allowed. Rows are copied in batches. The engine never drops, truncates or overwrites existing target rows.
  3. If a later batch fails or you cancel, batches already committed stay in the target.
  4. Validate results — compares row counts and some null counts. The result is PARTIAL. Matching counts do not prove values are identical.

Automated tests use in-memory stand-in databases. Verify against your own servers before a production cutover.

  • 90–100 high · 75–89 good · 50–74 needs review · below 50 weak. This is a rule of thumb, not a probability.
  • Exact name (ignoring case and separators) can reach 100.
  • Abbreviation or synonym matches cannot earn the “exact name” points, so they often score about 60.
  • If two targets score almost equally, the row is left as Needs review. You must choose.

  • Source and target are separate connections. One transaction cannot cover both databases.
  • Each INSERT batch is committed on the target. A later failure does not undo earlier batches.
  • Cancel is honoured at the next batch boundary.
  • Duplicate keys: fail the batch, or choose skip-duplicates. Existing target rows are never updated.

  • Database passwords stay in server memory. They are never logged, shown in errors, or saved in the data folder.
  • The browser cannot run arbitrary SQL, shell commands or DROP/TRUNCATE.
  • Production: HTTPS, BCrypt administrator hash from a secret store, host allow-list, least-privilege database accounts.

  • Projects and mappings are saved on disk without passwords. Dashboard counters and login lock-outs are still in memory.
  • CREATE TABLE SQL is shown in the preview but is not executed. Target tables must already exist.
  • Oracle: service name only (no SID / TNS). IPv6 hosts are not supported.
  • MariaDB, DB2 and SQLite are not registered. Every SQL Server / Oracle / PostgreSQL / MySQL pair is PARTIAL SUPPORT until tested on live servers.
  • Pages with a phase badge in the sidebar document future features and do not run in this build.

Every error shows a stable code, a correlation ID and a suggested action. Quote the correlation ID when asking for help; technical detail is only in the protected server log.
